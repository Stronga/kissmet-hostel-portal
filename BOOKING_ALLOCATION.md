# Booking And Allocation Foundation

## Scope

Phase 5 adds Cloudflare Workers + Hono + TypeScript admin APIs for application review, booking creation, availability, allocation, and transfers. It does not modify or depend on the legacy Django runtime.

Payments, payment slips, receipts, gateways, Mobile Money, resident dashboard, document uploads, maintenance, and announcements remain out of scope.

## Routes

All routes are under `/admin` and require an authenticated staff session.

- `GET /admin/applications`
- `POST /admin/applications`
- `GET /admin/applications/:id`
- `PATCH /admin/applications/:id/status`
- `GET /admin/bookings`
- `POST /admin/bookings`
- `GET /admin/bookings/:id`
- `PATCH /admin/bookings/:id/status`
- `GET /admin/availability?academicSessionId=1&residentId=1`
- `GET /admin/allocations`
- `POST /admin/allocations`
- `GET /admin/allocations/:id`
- `POST /admin/allocations/:id/transfer`
- `PATCH /admin/allocations/:id/status`

## Permissions

- `super_admin`: full access.
- `manager`: application, booking, and allocation read/write.
- `reception`: application intake/review plus booking/allocation operations.
- `accounts`: booking read only for Phase 6 payment work.
- `maintenance`: no application, booking, or allocation management.
- `resident`: no `/admin` access.

Server-side middleware enforces `application:*`, `booking:*`, and `allocation:*` permissions.

## Application Lifecycle

Application creation allocates `application_number` on the backend from `application_number_sequence`.
Callers provide `residentId`, `academicSessionId`, and optional notes only.
The generated format is `KSM-APP-0001`, `KSM-APP-0002`, and so on.

Allowed transitions:

- `draft -> submitted`
- `draft -> cancelled`
- `draft -> archived`
- `submitted -> under_review`
- `submitted -> cancelled`
- `under_review -> approved`
- `under_review -> rejected`
- `approved/rejected/cancelled -> archived`

Arbitrary transitions are rejected. Review start, approval, and rejection record reviewing staff and review timestamp. Decision notes are stored in `applications.decision_notes`.

Application approval does not allocate a bed. Approval only makes the application eligible for booking.

## Booking Lifecycle

Bookings are created only from approved applications. Each booking belongs to one resident, one academic session, and one approved application.

Statuses remain:

- `pending`
- `confirmed`
- `cancelled`
- `expired`
- `completed`
- `archived`

Allowed transitions:

- `pending -> confirmed/cancelled/expired/archived`
- `confirmed -> completed/cancelled/archived`
- terminal states may only archive.

The intended workflow is:

```text
approved application -> pending booking -> payment verification (Phase 6) -> confirmed booking -> bed allocation
```

`pending` is the state Phase 6 will make payment-gated. No payment state is faked in Phase 5.

## Booking Numbers

Booking numbers are generated by the service using `booking_number_sequence`.

Format:

```text
KSM-BKG-0001
```

The generated number is not the raw D1 primary key. Allocation uses a compare-and-swap update on the sequence row, and `bookings.booking_number` remains unique as the final concurrency guard.

## Room Rates

Booking creation requires an active `room_rates` row for the selected room and academic session. The active rate is copied into `bookings.total_amount_minor` and `bookings.currency`, preserving historical booking price if room rates later change. Money remains integer minor units, defaulting to `GHS`.

New bookings also persist the pricing source:

- `bookings.priced_room_id`: the room selected when the booking was priced.
- `bookings.priced_room_rate_id`: the active `room_rates` row used at booking creation.

The captured `total_amount_minor` and `currency` remain the booking's financial basis. Payment verification, confirmation thresholds, receipts, refunds, and payment-attention handling continue to use that captured basis. Verified payments are not automatically altered by allocation or transfer decisions.

## Availability

Availability checks:

- academic session
- active room rate for the room/session
- room status is `available`
- bed status is `available`
- bed has no active allocation
- non-archived bed inventory does not exceed room capacity
- room gender policy matches resident gender when known

## Allocation Lifecycle

Allocation creation verifies:

- booking exists
- booking belongs to the resident
- booking and allocation session match
- booking status is `confirmed`
- selected bed belongs to the booking's priced room, or to a room with the same active session rate and currency
- bed exists and is available
- room is available
- bed has no active allocation
- resident has no other active allocation for the same session
- gender policy is satisfied

Allocation history is preserved. Ending, cancelling, transferring, or archiving changes status instead of deleting rows.

Pending, cancelled, expired, completed, and archived bookings cannot receive a new active allocation.

The allocation service rejects cross-room allocation when the destination room's active rate for the booking's session differs from the booking's captured `total_amount_minor` or `currency`.

## Transfers

A transfer validates the destination bed first. It then marks the old active allocation as `transferred` with end/release timestamps and creates a new active allocation for the destination bed. The old bed assignment remains as history, and the active-allocation unique indexes remain the final concurrency guard.

Same-room transfers do not reprice the booking.

Cross-room transfers are allowed only when the destination room's active rate for the same academic session has the same amount and currency as the booking's captured financial basis. Same-priced rooms are treated as interchangeable for this version. Differently priced cross-room transfers are rejected; the service does not create adjustment invoices, credits, automatic repricing, or mutations to historical room-rate records.
